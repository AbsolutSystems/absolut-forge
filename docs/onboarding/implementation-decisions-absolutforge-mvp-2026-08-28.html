Review decyzji implementacyjnych — AbsolutForge MVP / Phase 5 Ship

Data: 2026-08-28 · Raport po finalnym review implementacji · 8 decyzji, ryzyko skumulowane: średnie

TL;DR

Phase 5 dostarcza explicit-only, lokalny closeout: Review zapisuje źródłowy fingerprint, Ship tworzy Feature Record i Executive Summary po jednym approval gate, a następnie wykonuje journalowaną transakcję z lokalnym commitem. Finalny gate zwrócił PASS, a AC fulfillment wynosi 15/15.

Decyzje poniżej są głównie potwierdzeniem granic bezpieczeństwa i własności artefaktów. Akceptacja dotyczy zakresu oraz odwracalności tych wyborów; nie otwiera kolejnej bramki jakości kodu.

Decyzje wymagające akceptacji

DEC-001 Własność fingerprintu

Źródło
01-contracts.md, Task 1 i sekcja fazy
Oryginalna uwaga
Ship remains a local closeout: Review owns source scope/fingerprint and Ship validates it before render and transaction mutation.
Zweryfikowany kontekst i uzasadnienie
Review jest jedynym świeżym, read-only oceniajacym zakres; Ship nie może sam definiować podstawy review. Canonical contract i skills/review/SKILL.md implementują dokładnie tę granicę.
Alternatywa
Ship mógłby ufać opisowi Review albo wyliczać własny zakres; zwiększałoby to ryzyko stale summary i scope drift.
Skutek / ryzyko
Zmiana źródła po Review zatrzymuje closeout i wraca do Review. Ryzyko operacyjne: niski–średni koszt dodatkowego odczytu.
Odwracalność
Wysoka na poziomie promptu/kontraktu; zmiana wymagałaby jednak ponownego uzgodnienia własności Review.

Czy akceptujesz DEC-001: Review pozostaje właścicielem zakresu i fingerprintu, a Ship wyłącznie go sprawdza? (Akceptuję / Proszę zmienić)

DEC-002 Canonical contract jako źródło ADR

Źródło
01-contracts.md, Task 2
Oryginalna uwaga
Aligned the ADR's freshness baseline, raw-path ordering, and path-only HTML policy with the canonical contract.
Zweryfikowany kontekst i uzasadnienie
ADR opisuje decyzję i konsekwencje, natomiast pełne schematy pozostają w references/artifact-contracts.md. Dzięki temu regex, manifest i link policy nie rozjeżdżają się między artefaktami.
Alternatywa
Duplikowanie pełnego schematu w ADR; odrzucone jako źródło rozbieżności.
Skutek / ryzyko
Przyszłe zmiany muszą aktualizować canonical contract i sprawdzić ADR; ryzyko dokumentacyjne niskie.
Odwracalność
Wysoka, o ile zachowana jest jedna wskazana własność schematu.

Czy akceptujesz DEC-002: ADR pozostaje zwięzłym zapisem decyzji, a dokładny kontrakt ma jednego właściciela? (Akceptuję / Proszę zmienić)

DEC-003 Fingerprint dopiero po finalnej ocenie

Źródło
02-review-and-harness.md, Task 1
Oryginalna uwaga
Review now records the canonical raw-byte manifest and SHA-256 only after the final assessment and before Complete; unsafe or stale scope remains an input blocker.
Uzasadnienie
Wczesny fingerprint nie chroniłby przed zmianą w fix loop. Końcowy manifest jest zapisany tuż przed Complete, a Ship wykonuje trzy kontrole świeżości.
Skutek / ryzyko
Review zapisuje większy artefakt, ale eliminuje ciche podsumowanie nieaktualnego stanu. Ryzyko niskie.
Odwracalność
Średnia: można zmienić moment zapisu, lecz wymaga to zmian obu kontraktów i testów.

Czy akceptujesz DEC-003: niebezpieczny lub zmieniony scope jest blockerem wejścia do Ship? (Akceptuję / Proszę zmienić)

DEC-004 Handoff explicit-only i lokalny

Źródło
02-review-and-harness.md, Task 2
Oryginalna uwaga
Claude and Codex references provide standalone repository-relative Ship handoffs; Review Codex metadata remains unchanged with explicit-only activation.
Uzasadnienie
Ship nie może “wchodzić” samoczynnie ani dostać uprawnień zdalnych. Handoff przekazuje tylko dopasowane ścieżki Brief/Review.
Skutek / ryzyko
Użytkownik musi wywołać Ship jawnie; zyskujemy brak konfliktu z AbsolutPowers i brak nieautoryzowanego push/PR.
Odwracalność
Wysoka, ale włączenie implicit invocation byłoby zmianą bezpieczeństwa i wymagałoby osobnej decyzji.

Czy akceptujesz DEC-004: Ship jest explicit-only i local-only we wszystkich handoffach? (Akceptuję / Proszę zmienić)

DEC-005 Jeden host-agnostic prompt Ship

Źródło
03-ship-skill.md, Task 1
Oryginalna uwaga
Links the canonical Ship contract and makes the validation, three fingerprint checks, exact preview, journaled local transaction, recovery, and no-remote boundaries executable in one host-agnostic prompt.
Uzasadnienie
Wspólne ciało skillu ogranicza rozjazd między Claude i Codex; różnice narzędziowe pozostają w referencjach harnessu.
Skutek / ryzyko
Prompt jest dłuższy i wymaga starannego utrzymania, ale unika dwóch divergent implementations. Ryzyko średnie, kompensowane testami kontraktowymi.
Odwracalność
Wysoka: można rozdzielić integrację bez zmiany kontraktu, lecz nie jest to potrzebne dla MVP.

Czy akceptujesz DEC-005: jedno wspólne ciało Ship z cienkimi mappingami harnessu? (Akceptuję / Proszę zmienić)

DEC-006 Brak drugiego review gate w Ship

Źródło
03-ship-skill.md, Task 1 i sekcja fazy
Oryginalna uwaga
Ship stays a local closeout stage: no second review gate, no automatic remote integration, and no archive mutation before explicit fingerprint-bound approval.
Uzasadnienie
Review jest zamknięciem jakościowym; Ship ma mechanicznie utrwalić zaakceptowany stan po jednym preview/approval. Drugi review odtwarzałby ciężką ceremonię, którą projekt celowo redukuje.
Skutek / ryzyko
Ochrona opiera się na finalnym Review, fingerprintach, preview i transaction recovery. Ryzyko akceptowalne dla MVP przy jasnym handoffie.
Odwracalność
Wysoka; dodatkowy audyt można uruchomić ad-hoc przez review, bez zmiany Ship.

Czy akceptujesz DEC-006: Ship nie uruchamia automatycznej triady ani drugiego review? (Akceptuję / Proszę zmienić)

DEC-007 Testy kontraktowe zamiast runtime implementation

Źródło
04-tests-and-docs.md, Task 1
Oryginalna uwaga
Added deterministic text-contract coverage for the Review fingerprint handoff, Ship lifecycle, rendering safety, local-only boundaries, and pure fingerprint/journal/commit-subject fixtures.
Uzasadnienie
Repozytorium przechowuje skill contracts, a nie runtime engine. Deterministyczne testy tekstowe sprawdzają wszystkie AC bez model calls, mutacji repozytorium i remote side effects.
Skutek / ryzyko
Testy nie wykonują prawdziwej transakcji Ship; jest to świadome ograniczenie MVP i osobny temat walidacji produktowej. Ryzyko średnie.
Odwracalność
Wysoka; testy behavioral można dodać w Phase 7.

Czy akceptujesz DEC-007: Phase 5 dowodzi kontraktu statycznie, bez uruchamiania prawdziwej transakcji? (Akceptuję / Proszę zmienić)

DEC-008 Dokumentacja opisuje implementację i recovery

Źródło
04-tests-and-docs.md, Task 2
Oryginalna uwaga
Marked Ship as implemented across product and skill documentation, including native commands, transactional recovery, and no-remote boundaries.
Uzasadnienie
Nowy kontekst sesji ma rozumieć Ship bez pamięci rozmowy. Dokumentacja wskazuje Feature Record, Executive Summary, approval, journal/recovery i brak push/PR/merge/deploy.
Skutek / ryzyko
Więcej tekstu do utrzymania; testy foundation i kontraktowe wykrywają brak odkrywalności. Ryzyko niskie.
Odwracalność
Wysoka; dokumentację można aktualizować bez zmiany workflow.

Czy akceptujesz DEC-008: dokumentacja produktu ma od teraz przedstawiać Ship jako zaimplementowany etap MVP? (Akceptuję / Proszę zmienić)

Interakcje i konsekwencje

DEC-001 + DEC-003 tworzą łańcuch świeżości: Review zapisuje baseline, Ship go nie redefiniuje, a każda zmiana wraca do Review. DEC-004 + DEC-006 ograniczają skutki uboczne: nawet poprawny closeout pozostaje jawny, lokalny i bez drugiej ceremonii. DEC-005 + DEC-007 przenoszą różnice harnessu i dowód poprawności do cienkich mappingów oraz testów kontraktowych. Najważniejsza nierozwiązana konsekwencja to brak runtime behavioral testów transakcji — świadomie odłożony do Phase 7.
