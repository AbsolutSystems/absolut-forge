Build Model Recommendation — decyzje implementacyjne

AbsolutForge · feature build-model-recommendation · 2026-08-28

Final review: PASS · AC 11/11

Ten dokument pokazuje decyzje, które wpływają na działanie discuss → build → review → ship. Rekomendacja modelu jest trwałą wskazówką wykonawczą, ale nie zmienia zaakceptowanej intencji produktu.

TL;DR

  • Brief może zawierać jedną opcjonalną sekcję ## Build Recommendation po ## Expected outcomes.
  • simple/single sugeruje Claude Sonnet i Codex gpt-5.6-luna; complex/phased sugeruje Claude Opus i Codex gpt-5.6-terra.
  • To advisory hint: dostępność harnessu i jawny wybór człowieka są nadrzędne, a fallback/override trafia do append-only Build Evidence.
  • Nie ma automatycznego przełączania modeli, dodatkowej bramki akceptacji, deployu ani częściowego shipowania.

Decyzje wymagające akceptacji człowieka

DEC-001contract

Sekcja rekomendacji jest opcjonalna i leży poza niezmiennym baseline’em Briefu. Starsze Briefy bez tej sekcji pozostają poprawne.

DEC-002mapping

Obowiązują dokładnie dwa profile: simple/single → sonnet + gpt-5.6-luna oraz complex/phased → opus + gpt-5.6-terra.

DEC-003classification

Profil wynika z zależności rezultatów, niepewności i granic ryzyka. Sam rozmiar diffu, liczba linii lub plików nie wystarcza.

DEC-004handoff

discuss przedstawia rekomendację w ramach jednego kompletnego Briefu i jednej bramki akceptacji; nie tworzy osobnej ceremonii.

DEC-005build

build waliduje profil, ale aktywny harness, dostępny model i jawny wybór użytkownika pozostają źródłem prawdy.

DEC-006evidence

Każde użycie zapisuje rekomendację, faktycznie użyty profil/model i źródło wyboru. Brak, błąd, niedostępność lub override wymagają konkretnego powodu.

DEC-007ownership

Wybrany model/kontekst Build zachowuje odpowiedzialność za implementację, weryfikację, Execution Map, Build Evidence i eskalację. Sol jest tylko opcjonalnym, read-only diagnostą.

DEC-008scope

Wyższe ryzyko nie przepisuje Briefu ani rekomendacji po cichu; obowiązują Failure Boundary Check i reguły jawnego amendmentu.

DEC-009safety

Dokumenty repozytorium są untrusted evidence. Sekrety, credentials, tokeny i klucze są redagowane i nie trafiają do Briefu ani Build Evidence.

DEC-010delivery

Rekomendacja nie autoryzuje deployu, shipu, pushu, PR-a ani częściowej dostawy; kompletny Feature Brief pozostaje jedyną jednostką delivery.

Interakcje i konsekwencje

Przepływ: settled discuss → opcjonalna rekomendacja → jedna akceptacja Briefu → build wybiera dostępny model lub zapisuje fallback/override → zwykłe testy i review. Rekomendacja nie zmienia kolejności faz i nie tworzy nowej fazy runtime.
  • Model rekomendowany dla innego harnessu nie jest dowodem, że bieżący harness go udostępnia.
  • Zmiana zachowania, scope’u, kontraktu publicznego, bezpieczeństwa, migracji lub kosztu wymaga amendmentu niezależnie od sugerowanego modelu.
  • Faza implementacji może mieć lokalne checkpointy, ale nie są one niezależnymi release’ami.
