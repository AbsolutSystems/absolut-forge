# AbsolutForge 0.10 — Token-efficiency implementation plan

## Purpose

Validate the 0.10 token-efficiency review against `main` and define the next
implementation sequence. This is a maintainer plan, not a canonical Feature
Brief or lifecycle `implementation-plan.md`; each behavior change still needs
accepted intent through the ordinary AbsolutForge lifecycle.

The optimization target is total host-measured tokens per accepted feature,
with Review quality and lifecycle correctness held constant. Static character
counts remain diagnostic evidence only.

## Repository validation

Validation was performed on 2026-09-10 against release `0.10.0`. The worktree
was clean before this document was added. The complete local suite passed:

```text
rtk python3 -m unittest discover -s tests -v
Ran 50 tests ... OK
```

The existing synthetic benchmark also passed. Planned owner packages are
29,249–29,271 serialized characters across its small/medium/large fixtures,
versus 52,155–53,587 characters at the pinned 0.6 baseline. The benchmark
correctly reports every live metric as unavailable.

## Constraints

- `skills/` and canonical references remain the behavioral sources of truth.
  Host mechanics continue to be authored only in `references/*-tools.md`.
- Any generated projection is explicitly non-authoritative, reproducible from
  canonical sources, and protected by a stale-output test. Never hand-edit it.
- Briefs, plans, Build Evidence and Git remain canonical durable state.
  Bootstrap/final packages are read-only caches and may be discarded.
- Every clean checkpoint remains sufficient for recovery even when rotation is
  skipped.
- Bounded workers, worker-owned implementation/test edits, exact-profile stop
  behavior, targeted final verification and fresh independent Review remain
  unchanged.
- Optimization claims use host counters. Character/4 estimates and files read
  are reported separately and never presented as token savings.

## Delivery sequence

### WP-1 — Measurement contract and baseline gate

**Goal:** make accepted-feature cost observable before changing routing or
rotation.

**Changes**

- Define a versioned, secret-redacted benchmark run record for role/stage,
  provider/model/effort, host input/output/cached tokens when available,
  owner/worker launch counts, rotation reason, correction attempts, gate
  results, Review blockers, wall time and accepted/not-accepted outcome.
- Add a read-only aggregation command under `tools/` that accepts exported host
  records and reports per-feature and per-role totals. Keep raw host traces out
  of feature artifacts and Git.
- Extend `docs/runtime-benchmark.md` with the controlled-run protocol: fixed
  accepted intent, base revision, gates and host configuration; paired ordering
  or randomization; failures and corrections included; independent Review
  required.
- Create a corpus manifest for 10–20 replayable historical features spanning
  small/medium autonomous and medium/large planned work. The current repository
  contains only one retained feature execution, so corpus selection or fixtures
  require external history/host runs.

**Acceptance**

- Schema rejects invented token values and distinguishes unavailable, measured
  and estimated fields.
- Aggregation cannot count an unaccepted/incomplete run as accepted-feature
  cost and retains failed attempts in the cost of a later accepted run.
- A synthetic fixture proves role totals, correction attribution and redaction;
  a real baseline dataset is captured before WP-2 changes rotation behavior.

### WP-2 — Value-triggered Codex rotation and boundary economics

**Depends on:** WP-1 baseline capture.

**Goal:** amortize Sol rehydration without weakening durable recovery.

**Changes**

- Replace checkpoint-triggered Codex rotation with explicit value triggers:
  reliable host context pressure above a configured threshold; a substantial
  `PC-`/replan or long diagnosis; entry into a materially independent high-risk
  phase; the final-verification independence boundary; inability to compact
  safely; or an explicit later Build invocation.
- Keep every implementation/test checkpoint rotation-safe, but do not emit
  `ROTATE` solely because the checkpoint exists. Record the transient rotation
  reason in benchmark telemetry, not Build Evidence.
- Preserve a fresh owner at the start of each new Build invocation and a fresh
  context before final verification when the existing independence rule
  applies.
- Add a plan-compilation question: merge an adjacent task/outcome boundary
  unless it has concrete recovery, dependency, independent acceptance,
  ownership, risk or context value. Preserve the existing prohibition on
  merging unrelated outcomes and the rule against a fixed task count.

**Acceptance**

- Runtime-contract tests prove that a clean checkpoint is resumable but no
  longer an unconditional rotation trigger, and prove every retained trigger.
- A multi-task simulated Build can retain one owner across ordinary coherent
  checkpoints and still rehydrate successfully at any checkpoint.
- Compared with WP-1 baseline, owner launches and rehydration tokens fall
  without regression in accepted-feature rate, correction attempts, escaped
  Review blockers or lifecycle tests. If not, retain the old policy.

### WP-3 — Deterministic owner and final-verification packages

**Depends on:** WP-1. May run in parallel with WP-2 implementation after the
baseline is frozen.

**Goal:** remove mechanical navigation from owner startup and final assembly.

**Changes**

- Refactor reusable Markdown/Git parsing out of `tools/context_package.py`
  without changing current `resume` or `capsule` behavior.
- Add an `owner` projection for autonomous and planned Build that derives:
  Brief path/status, strategy/methodology, base/head, execution artifact,
  frontier/current outcome or task, relevant dependency facts, unresolved
  Review blockers and evidence freshness. Validate only reconstructible facts;
  fail closed on contradictory state.
- Add a `final` projection containing accepted outcomes/constraints/amendments,
  plan/outcome coverage, base/head, changed paths, validated test inventories,
  freshness, pending final obligations, unresolved observations/blockers and
  the exact diff range. Keep the full diff out of duplicated JSON; the owner
  must still inspect the complete range.
- Add deterministic checks for changed-path ownership, overlapping task write
  surfaces, task/schema completion, stale evidence by source/test commit,
  checkpoint cleanliness, legal lifecycle transition and unresolved blocking
  Review findings. Return `PASS` plus semantic exceptions needing owner review.

**Acceptance**

- Output is identical for equivalent durable state regardless of completed
  history length or prior conversation.
- Dirty, stale, ambiguous, unowned and contradictory fixtures fail closed with
  actionable errors; helpers never mutate artifacts, run embedded commands or
  treat derived state as authority.
- Existing capsule compatibility tests remain green for modern and legacy
  artifacts.
- Final-package tests prove complete accepted coverage and diff pointers while
  retaining semantic test-quality, boundary classification and full-diff review
  as owner responsibilities.

### WP-4 — Generated effective runtime experiment

**Depends on:** WP-1 baseline; preferably uses WP-3 parsing/validation.

**Goal:** determine whether compiling the effective Codex owner instructions
reduces total input enough to justify generated distribution artifacts.

**Changes**

- Build a deterministic compiler for the exact Codex × strategy × lifecycle
  states under test, starting with planned Building and planned final
  verification. It selects tagged canonical clauses from the Build skill,
  common/strategy runtime and Codex mapping.
- Generated files contain provenance and source hashes and are explicitly
  non-authoritative. The compiler, never a maintainer, writes them. Canonical
  schemas remain links/escalations rather than duplicated templates.
- Add a generation check that fails when committed output differs from compiler
  output, a rule-coverage test mapping each projected obligation to its source,
  and packaging/link tests.
- Expand to autonomous or other hosts only after the Codex experiment shows a
  measured end-to-end benefit. Host-specific source text remains in the host
  reference even if a generated distribution projection contains it.

**Acceptance**

- Zero manually authored normative sentence exists only in generated output.
- A canonical-source change makes the generation check fail until regeneration.
- Lifecycle, worker ownership, exact-profile failure, verification and Review
  gates match the uncompiled path in contract tests.
- Host-measured accepted-feature cost improves beyond run-to-run variance; if
  startup tokens shrink but total cost or quality worsens, do not adopt the
  generated runtime path.

### WP-5 — Worker-effort experiment and policy decision

**Depends on:** WP-1 tooling and enough standard-task corpus runs. Run after
rotation/projection changes independently so causal effects stay visible.

**Goal:** choose Luna `high` or `xhigh` for standard work by accepted-task total
cost, not per-turn price or intuition.

**Changes**

- Run paired standard-task trials with identical capsules, repository bases and
  gates for Luna `high` and `xhigh`.
- Report worker input/output tokens, first-pass acceptance, correction and
  redispatch counts, owner validation tokens, wall time and escaped Review
  blockers. Segment by task size/risk instead of averaging incompatible work.
- Change `references/codex-tools.md`, README and locked profile tests only if a
  predeclared decision rule selects a winner. Otherwise retain `xhigh` and
  record the inconclusive result outside runtime prompts.

**Acceptance**

- Every comparison includes the full accepted-task cost through owner
  validation and independent Review.
- The selected profile is not worse on escaped blockers or accepted-task rate
  and has a statistically/operationally meaningful total-cost advantage.
- No dynamic auto-router is introduced in this pass.

## Experiment order and rollback

Run the baseline, then isolate changes in this order:

1. value-triggered rotation;
2. owner/final deterministic packages;
3. generated effective runtime;
4. Luna standard-effort comparison.

Use separate paired runs for each change before combining winners. Every
behavioral change is documentation/tooling and can roll back by restoring the
prior host mapping/runtime path; canonical feature artifacts require no
migration. Projection caches can be deleted and regenerated.

The primary decision metric is total host-measured tokens per accepted feature.
Guardrails are accepted-feature rate, escaped Review blockers, correction
attempts, final verification validity and successful clean resume. Owner and
worker token splits, launches and wall time are diagnostic secondary metrics.

## Deferred work

- Papercuts retrieval, until traces demonstrate repeated diagnosis signatures
  with enough frequency to repay retrieval complexity.
- Dynamic model routing or automatic effort selection.
- Changes to fresh independent Review context.
- Broad-suite reduction beyond the existing affected-test doctrine.
- Persistent bootstrap/final artifacts or lifecycle schema changes.
