# Autonomous Build Runtime

Use with [common](common.md). The high-capability builder owns the whole accepted feature. [Artifact contracts](../references/artifact-contracts.md) own lifecycle and evidence schemas.

## Start and resume

Entered internally by `build` after strategy resolution; consume the canonical Brief path and resolved selection. At initial Ready start, read accepted intent/amendments, artifact start/evidence sections and the [verification doctrine](../references/verification-doctrine.md). Require a non-detached feature branch, committed Ready Brief, clean worktree and empty index. The permitted consultation report is the only exception. Reject stale execution artifacts. Record HEAD as base, autonomous strategy, selection reason, not-applicable methodology and chosen artifact; set Building and checkpoint before source edits, including an allowed consultation report when present.

At Building, confirm recorded branch/base, strategy and methodology. Planned state routes through `build` to the planned runtime with its recorded methodology; never convert it. Read accepted intent/amendments, current outcome evidence, optional map frontier and relevant source/tests. Do not preload all past outcomes or checkpoint diffs. Current Git state is implementation truth. Reconcile dirty/mid-outcome work using recorded evidence without overwriting unrelated changes or claiming a clean checkpoint. Open sibling Review blockers are required input. Consultation is optional evidence and cannot authorize changed intent.

## Coherent outcome loop

Choose an accepted outcome and inspect named symbols/paths, direct callers, targeted tests and local dependencies before broader searches. Use an optional execution map for dependent outcomes, uncertainty or durable resume; consult its canonical schema only when creating/interpreting it. Never adopt a planned artifact or require a task recipe for autonomous work.

Identify concrete applicable test obligations: primary accepted behavior, introduced failure/boundary, material state/data invariant, owned seam contract and fixed-defect regression. Tests prove observable repository-owned results, state changes, errors or meaningful outbound contracts. Mocks at external seams are valid when assertions establish owned behavior. Mock setup, framework internals, private structure and insignificant call counts do not satisfy obligations. Consult doctrine for uncertain classification, materially revised obligations or exemptions. Never invent inapplicable tests or weaken existing assertions merely to reach green.

Before implementation, apply [autonomous outcome routing](../references/model-routing.md#autonomous-outcome-routing). For a mixed-risk outcome, first separate and record the high-tier decision when that creates a genuine boundary, then reclassify the residual implementation on its own execution risk; one high concern does not make the entire outcome high. Delegate a bounded low/standard outcome to one fresh worker through the active host mapping by default, without a planned artifact or strategy change. Keep it inline only under the routing contract's owner-interaction exception and record the reason. If residual implementation stays high, record the concrete risk preventing delegation. The Build owner retains whole-feature ownership, validation, lifecycle and checkpoint commits.

Implement within accepted intent, inline or through that worker. Include the canonical Scout boundary in every delegated outcome package. The executor may repair a qualifying scout issue only inside the settled outcome and owned paths; it returns larger or behavior-changing observations without editing them. The executor runs the smallest relevant unit-test target and cheap build/type/lint gate. A worker fixes failures inside its settled outcome and write surface and repeats that focused gate until green; it returns early only at its routing boundary. It returns the exact test files and named cases added or changed with commands and results, plus any scout fix or deferred observation. The owner validates that inventory and reruns a worker's green gate only when its evidence is incomplete, stale or creates a concrete doubt. Targeted integration and e2e checks for changed boundaries belong at final verification. Complete an outcome only when meaningful tests are green or an allowed exemption names its reason and closest observable check. Inspect the outcome diff and maintain relevant documentation. Record material decisions and unresolved facts without expanding the feature. Classify failures found during owner validation or final verification before editing: send local low/standard corrections to a fresh bounded worker with the failure and relevant current evidence; retain only high-tier corrections with the owner.

Append a compact Outcome checkpoint: commit reference, result, named cases/commands/results or valid exemption, new durable facts. Update any execution map and create a local outcome checkpoint containing only owned paths. Use `this checkpoint` when evidence is committed with its own entry; Git resolves the introducing revision. Do not repeat global final-evidence fields at each outcome. Existing full intermediate entries remain append-only history.

Clean checkpoints must permit recovery from repository state without conversation. Discard raw logs/dialogue and follow the active host's fresh-owner continuation after a substantial outcome checkpoint and before final verification. A verified checkpointed inventory or classification is durable evidence; do not reconstruct it without a concrete invalidating change or contradiction. Save captures unresolved context, not dirty source durability. Evidence that changes accepted behavior/scope, public contracts, security/data, migration or material cost requires an accepted amendment and relevant canonical interpretation before implementation continues.

## Final verification

Deliberately reload all accepted outcomes/constraints and amendments, outcome coverage and complete `base_commit..HEAD`. Recheck coverage and inspect the full diff for scope, cross-outcome inconsistency and garbage. Build the affected test set from that evidence and the validated executor inventories. Reuse current green worker results; rerun only targets made stale by later edits or supported by a concrete doubt, plus focused cross-outcome regressions. Run targeted integration/e2e checks for changed boundaries and exercise the primary accepted path. A full layer or project suite requires the doctrine's cross-cutting, unreliable-selection, repository-mandate, or missing-CI justification; otherwise record the required CI gate that owns broad regression coverage.

If the primary path cannot be exercised within scope, record why and the closest whole-feature check actually performed under the doctrine. Compilation/packaging alone is not primary-path exercise unless producing that artifact is the accepted behavior. Correct failures and verify before delivery, checkpointing coherent corrections.

Read the complete final Build Evidence schema from artifact contracts. Append every current field, named tests/results or exemptions, whole-feature path, decisions/deviations, execution state and Scout disposition. Name each qualifying scout fix with its focused proof and each deferred observation with the boundary it crossed; use `none` only when nothing material was found. Validate freshness against source/tests being delivered; set In Review and checkpoint the handoff. Any later source/test change invalidates final evidence: repeat affected final verification and append a new complete entry. Lifecycle-only and Review-artifact commits do not invalidate it.

Read the [harness contract](../references/harness-command-contract.md) for the active-host Review handoff. End with resolved Brief and Review paths and a copy-ready continuation. Emitting it does not invoke Review or authorize Ship.
