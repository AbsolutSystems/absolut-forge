## Problem

The existing AbsolutPowers workflow relies on detailed task decomposition and
multiple QA, planning, phase, implementation, and multi-agent review gates. This
creates high token usage and long delivery cycles, while final review can still
find defects. Strong models such as GPT-5.6 Sol and Opus should be able to own
local implementation planning when they receive a precise intent, durable
context, and clear outcome boundaries.

AbsolutForge will test a different product philosophy: control the delivered
result rather than prescribing and reviewing every implementation step.

## Users

- Developers using frontier coding models in Claude Code or Codex.
- Teams that want durable feature intent and review evidence without a heavy
  planning pipeline.
- Human PR reviewers who need a concise explanation of the final change.

## Expected behavior (high-level)

The standard workflow is `discuss -> build -> review -> ship`.

- `discuss` produces one accepted Feature Brief and durable ADRs.
- `build` reads the complete Brief, creates an Execution Map only when useful,
  implements autonomously, and owns focused plus final verification.
- `review` uses one independent fresh context and reports only evidence-backed
  `BLOCKING` and `FOLLOW-UP` findings.
- `ship` runs after review fixes, consolidates active artifacts into a Feature
  Record, generates a human-facing Executive Summary HTML, handles approved
  project-memory promotion, and prepares a local commit and PR description.
- `debug` and `tech-debt` remain independent, autonomous tools outside the core
  delivery chain.

## Shared architectural context

- `docs/product-vision.md` is the durable source of truth for accepted product
  behavior and cross-phase contracts.
- Exact artifact schemas and lifecycle: [`references/artifact-contracts.md`](../../../references/artifact-contracts.md).
- Memory routing and promotion: [`references/project-memory.md`](../../../references/project-memory.md).
- Native command and handoff rules: [`references/harness-command-contract.md`](../../../references/harness-command-contract.md).
- Separate repository and product identity from AbsolutPowers.
- Product name: **AbsolutForge**; repository: `absolut-forge`; plugin identifier:
  `absolutforge`.
- One host-agnostic skill tree with thin Claude Code and Codex integrations.
- No Pi or Grok support in the MVP.
- No SessionStart hook and no globally injected pipeline context.
- Core skills are explicit-only; only `debug` may auto-trigger for a concrete
  failure.
- No hard-coded model dependency. The workflow is optimized for strong frontier
  coding models.
- AbsolutPowers and AbsolutForge must not be enabled together during normal use;
  the classic plugin remains separately installable and can be disabled.
- The original Feature Brief intent becomes immutable at `Ready`. Later changes
  require an explicit amendment.
- ADRs remain separate durable documents under `docs/adr/`.
- Cross-cutting memory lives in `absolutforge/project-memory.md`; package-local
  lessons live in scoped `CLAUDE.md`/`AGENTS.md` Gotchas.

## Shared decisions

- Outcome-oriented execution instead of detailed tasks and task-review gates.
- Conditional Execution Map owned by `build`, not a separate planning skill.
- One independent final review; no automatic triada.
- Final human documentation is generated by `ship` after all review fixes.
- Active feature artifacts are consolidated into one Markdown record and one
  self-contained HTML report at closeout.

ADRs for these cross-cutting decisions will be created during the relevant
implementation phases when their exact contracts are finalized.

## Phase dependencies

- Phase 1 establishes contracts and harness integration used by all later phases.
- Phase 2 defines the Feature Brief consumed by Phases 3-5 and by `debug` fixes.
- Phase 3 depends on the Brief contract from Phase 2.
- Phase 4 depends on final build evidence from Phase 3.
- Phase 5 depends on final review output from Phase 4.
- Phase 6 depends on the Brief and memory contracts from Phases 1-2 but can be
  implemented independently of Phases 3-5 after those contracts stabilize.
- Phase 7 validates the completed core workflow and standalone tools.

## Out of scope (whole epic)

- Pi and Grok harness integrations.
- `generate-tasks`, QA enrichment, plan review, per-phase review, implementation
  review, or automatic triada review.
- Porting `problem-discuss`, `qa-review`, `constitution`, module documentation,
  explain, learned-skills mining, or the full AbsolutPowers tool catalog.
- A global SessionStart hook.
- Automatic push, PR creation, or merge during `ship`.
- Running AbsolutPowers and AbsolutForge concurrently as overlapping workflows.
- Formal trademark or domain registration work.

## Cross-cutting open questions

- Exact minimum supported versions of Claude Code and Codex will be determined
  from the integration primitives available during Phase 1.
- The comparative pilot needs 3-5 representative real changes selected during
  Phase 7.

## Discussion notes

- The product is intentionally not named or positioned as an AbsolutPowers
  "light" edition. It is a separate product with a different operating model.
- Feature Briefs carry product intent and observable outcomes, not detailed file
  lists or implementation steps.
- `build` may stop only for a material product decision, scope expansion,
  migration/security risk absent from the Brief, contradictory binding context,
  or a genuine external blocker.
- Executive Summary HTML is for human PR review and is generated only from the
  final post-review state.
